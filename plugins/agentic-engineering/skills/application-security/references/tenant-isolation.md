# Tenant isolation

A tenant is whoever the data belongs to: a company, a household, a customer account. Isolation
means nothing one tenant does can read, change or slow another tenant's data. It fails most
often not in the main table but in a place somebody forgot: a cache, a job, an export.

## Where the tenant comes from

One place: the verified session. The sign-in step resolves the caller to a tenant and stores it
server-side; every later step reads it from there.

- A tenant identifier in the URL, a header, a query or a body is **input**. If the product
  shows one (a path such as `/acme/projects`), compare it with the session's tenant and
  refuse on a mismatch. Never use it to select data.
- A user in several tenants picks one, and the server checks the membership before storing the
  choice. Switching tenant is a server-side change with a log line.
- When a membership ends, access ends with it. Check the membership on each request, or end
  that person's sessions for the tenant when it is removed. A tenant stored at sign-in and
  never looked at again outlives the membership.
- Background work has no session. Carry the tenant in the job itself and set it explicitly
  when the job starts.

## In the data layer

- **Every tenant-owned row carries the tenant.** Make it part of the key, so two tenants can
  never collide and a relation cannot point across tenants: primary key `(tenant_id, id)`,
  foreign keys that include `tenant_id`.
- **No function reads by identifier alone.** Give the data layer signatures that take the
  tenant on every call (`Get(tenantID, id)`, never `Get(id)`). A handler then cannot forget it.
- **Lists, counts, searches and exports are queries too.** The filter belongs in each of them.
- **Uniqueness is per tenant.** A unique index on `email` alone tells one tenant that another
  tenant already has that address. Index `(tenant_id, email)`.

## Row-level security in PostgreSQL: a second line, with limits

The database can refuse rows the application forgot to filter. Checked on PostgreSQL 17.11:

```sql
ALTER TABLE invoices ENABLE ROW LEVEL SECURITY;
ALTER TABLE invoices FORCE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON invoices
  USING      (tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::uuid)
  WITH CHECK (tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::uuid);
```

The application sets the tenant at the start of each transaction, with the third argument
`true` so the value ends with the transaction:

```sql
BEGIN;
SELECT set_config('app.tenant_id', $1, true);
-- the request's queries
COMMIT;
```

What that test run showed, and what to hold on to:

- **Use the transaction-local form.** A plain `SET app.tenant_id = ...` lasts for the whole
  connection. With a connection pool the next request, for another tenant, inherits it.
- **Keep `NULLIF(..., '')`.** After a transaction-local value ends, the setting reads as an
  empty string, not as missing. Without `NULLIF` the next query on that connection fails with
  a cast error instead of returning no rows.
- **Keep `FORCE`.** Without it the table's owner sees every row. Run the application as a role
  that does not own the tables and is not a superuser: a superuser, and any role with
  `BYPASSRLS`, ignores every policy.
- **No tenant set means no rows.** That is the safe failure. Test it.
- **It is not a wall against the application itself.** The application's role can set the
  value to any tenant. So this catches a forgotten filter; it does not contain someone who can
  run SQL as that role, for example through an injection flaw. If the product needs that
  boundary, each tenant needs its own database role that the application connects as for
  that tenant, with rights on that tenant's schema or database only and no way to become
  another tenant's role. A separate schema that one shared role can read is not a boundary.
  Say which you chose in the threat model.

Row-level security is added to the filters in the data layer, not instead of them. Migrations,
reports and maintenance jobs often run as a privileged role that skips the policies: give them
the same tests.

## Every other place data rests

| Place | Rule |
|---|---|
| Cache | The tenant is part of every key. A response cached for one tenant is never served to another: check shared caches and CDN rules for pages that hold tenant data |
| Files and object storage | A per-tenant prefix, chosen by the server. The access check runs before the file is read. No public bucket, no path built from a client's file name |
| Queues and jobs | The tenant travels in the message and is set before any query. A job that loops over tenants sets the tenant inside the loop |
| Search index | The tenant is a required filter added by the server, never an optional parameter |
| Exports and reports | Generated by the same data layer, stored under the tenant's prefix, fetched through the same access check |
| Logs, metrics and traces | Carry the tenant identifier, never the tenant's data. A support view of logs is itself tenant data |
| Email and notifications | The recipient list is built from the tenant's own members |
| Backups and copies | A copy in a test environment is still tenant data. Restore tests use the same isolation tests |

## Crossing the boundary on purpose

Support access, an administrator acting as a user, a report across customers: each is a
deliberate hole. Each needs its own narrow operation, a reason recorded at use, a log the
tenant could be shown, and a named person who approved the design. Adding one is an
escalation, not a refactor.
